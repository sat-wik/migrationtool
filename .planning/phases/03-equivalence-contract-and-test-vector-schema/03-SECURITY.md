## Trust Boundaries

| Boundary | Description | Data Crossing |
|----------|-------------|---------------|
| mt (host side) -> qemu-arm guest | the request file crosses into the emulated guest; the result frame, exit status and streams cross back and are classified only from the runner's record and the frame | see description (03-01) |
| guest -> host kernel (qemu-arm user mode) | guest syscalls are passed to the host kernel by QEMU, inside the CI container | see description (03-01) |
| workflow -> run_vectors container | the image, the static mt binary and read-only inputs cross into a container with no network | see description (03-01) |
| policy file (committed or customer-supplied) -> mt-contract loader | TOML text crosses into the code that decides which UB action the harness checks | see description (03-02) |
| policy -> evidence reports | the override report and the default change cross into evidence that a reviewer reads | see description (03-02) |
| github.com (TRACTOR repository) -> work directory | untrusted JSON arrives through the one networked step this phase adds | see description (03-03) |
| vector and corpus files -> mt-vectors parsers | JSON from our executor, from TRACTOR or from a customer later; parsed, never executed | see description (03-03) |
| corpus directory -> evidence | file names and the index decide which vectors count as evidence | see description (03-03) |
| testbed/manifest.toml -> generated driver C | manifest text crosses into C source that is compiled and run | see description (03-04) |
| Phase 2 capture artifacts -> link step | the objects and capture.json cross from the capture evidence into the reference build | see description (03-04) |
| captured object code (upstream) -> host kernel, through qemu-arm user mode | guest syscalls reach the host kernel inside the run_guest container | see description (03-04) |
| executor -> corpus and provenance | stored vectors and their index become evidence for Phases 4, 5 and 11 | see description (03-04) |
| captured compile commands -> layout probe and TU recompilation | recorded flags decide how a type is laid out; a wrong flag gives a wrong layout | see description (03-05) |
| llvm-dwarfdump text -> layout parser | tool output parsed as data | see description (03-05) |
| guest memory bytes -> decoder -> vectors | raw bytes, including addresses, become evidence | see description (03-05) |
| guest heap bytes -> heap walk -> vectors | the C library's own heap structures become recorded evidence | see description (03-06) |
| manifest str values -> request file -> guest | declared strings cross into the guest as data | see description (03-06) |
| committed drop logs and seed indexes -> floor test | the files that decide whether the success line is met | see description (03-06) |
| manifest setup and local declarations -> generated driver C | declared calls, arguments, field paths and type texts become compiled code | see description (03-07) |
| setup outcome -> vector comparison | a setup result decides whether the entry ran | see description (03-07) |
| CI annotation text -> committed sample files | the sample crosses from the pinned image to the repository through notice text | see description (03-08) |
| committed sample -> later phases' offline tests | the sample is trusted as the reference for offline checks | see description (03-08) |
| adapter drop log -> phase completeness claim | a row explains why an entry has no vectors | see description (03-08) |
| Debian snapshot archive (bookworm-backports) -> image | the QEMU packages and any dependency they pull enter every stage derived from apt-base | see description (03-09) |
| snapshot.debian.org machine-readable API -> pin-discovery notice | informational version list; read as data, never executed | see description (03-09) |
| branch push -> GitHub Actions | pushes trigger pin-discovery, container, ci and testbed on the session branch; only a push to main publishes | see description (03-09) |
| image-a container -> probe guest | an assembled guest runs under qemu-arm inside the offline, read-only, unprivileged image container | see description (03-09) |
| session branch -> main | the PR merge publishes the image and changes the default branch | see description (03-10) |
| GHCR publish job -> README | the digest recorded here is what every later testbed run pulls | see description (03-10) |
| testbed annotations -> notice baseline | the re-baselined 02-22 file is what every later Phase 3 plan compares against | see description (03-10) |
| testbed job artifacts -> vectors job runner | `work.tar` and `replay.tar`, made from trees that upstream build code wrote in no-network containers, are unpacked on the runner, whose later steps `source` `$RUNNER_TEMP/ci-lib.sh` | see description (03-08 threat flag, code review WR-04) |

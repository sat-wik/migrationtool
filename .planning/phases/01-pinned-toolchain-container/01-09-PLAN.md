## Planning-time evidence (2026-10-09, this session; local rustup is 1.29.1, the pinned version)

- **rustup does not store the pinned bytes.** `sha256sum` of `toolchains/1.99.0-x86_64-unknown-linux-gnu/lib/rustlib/multirust-channel-manifest.toml` was 3aa2ac65... for the session's own install and 3bd93d33... for a fresh install. The pin, which equals the downloaded channel-rust-1.99.0.toml, is ce6dddc8.... For 1.72.1 the stored copies were d5d95662... and 28e24aa2... against the pin 77113b96.... rustup re-serializes the manifest on each install, so the first fix suggested in VERIFICATION.md (hash the stored manifest against the pin) would fail every build. It is not used. `update-hashes/<version>-<host>` holds only the first 20 hex characters of the manifest sha256 (ce6dddc886364f8d7865, 77113b9660855a5ab49e). That is a witness, not a binding.
- **A file:// mirror binds the pin.** A prototype did the following:
  1. Downloaded channel-rust-<version>.toml and checked it against the pin.
  2. Wrote the `.sha256` sidecar.
  3. Fetched the xz archives of [pkg.rustc|cargo|rust-std.target.x86_64-unknown-linux-gnu]. For 1.99.0 it also fetched clippy-preview and rustfmt-preview for the host, plus rust-std for thumbv7em-none-eabihf and x86_64-unknown-linux-musl.
  4. Checked each archive against the manifest's xz_hash.
  5. Ran `RUSTUP_DIST_SERVER=file://<mirror> rustup toolchain install <version> --profile minimal --no-self-update` with the pinned `-c` and `-t` flags.

  Results: 1.99.0 installed with 7 components (rustc commit b940084d7eb6..., LLVM 23.1.1) and 1.72.1 with 3 components, both exit 0. With HTTPS blocked (proxy set to 127.0.0.1:9) the mirror install still succeeded, while the control install from the default server failed. So rustup read only the mirror.

  Manifest facts:
  - Sections are `[pkg.<pkg>.target.<target>]` with the keys available, url, hash, xz_url and xz_hash.
  - Renames: `[renames.clippy]` has `to = "clippy-preview"` and `[renames.rustfmt]` has `to = "rustfmt-preview"`.
  - The minimal profile is rustc, cargo, rust-std and rust-mingw. rust-mingw has no Linux entry, and rustup skipped it.

  The prototype's awk ran under mawk 1.3.4, the same awk family as Debian bookworm's default.
- **Self-update.** Without `--no-self-update`, `rustup toolchain install` entered rustup's self-update path after installing. Inside the image, that path could replace the sha256-pinned rustup with whatever rustup release is current. `rustup toolchain install --help` lists `--no-self-update`.
- **Crates.**
  - c2rust-0.22.1.crate and cargo-mutants-27.1.0.crate match their pins, and each ships a Cargo.lock.
  - c2rust also ships the nightly rust-toolchain.toml from RESEARCH Pitfall 2, and the bins c2rust and c2rust-transpile.
  - `cargo metadata --locked` on each unpacked crate resolved with the packaged lockfile unchanged.
  - `cargo install --locked --root R --path P --version "=V" NAME` installs from the path package. It exits 101 when NAME or V differ from that package.
  - `--version` without a NAME is rejected by cargo's argument parser.

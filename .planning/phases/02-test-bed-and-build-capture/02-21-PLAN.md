## Claude's discretion (planner choices; record each in the SUMMARY)

Cause taxonomy. The allow-list decides; no list of known-bad options is kept for naming. Table: refusal, then `CcError`, then cause token.
- empty argv: `NotCompileOnly`, `not_compile_only` (unchanged)
- argv[0] not allow-listed: `CompilerNotAllowed`, `compiler_not_allowed` (unchanged)
- any argument after argv[0] that starts with `@`, operand or not: `HelperOption { flag }`, `helper_option` (kept: the driver reads options from a file)
- `-specs=<name>` with a name not in `SHIPPED_SPECS`, empty, or containing `/`, and every other argument that starts with `-specs`: `HelperOption { flag }`, `helper_option` (kept: the driver reads commands from a spec file)
- `-flto*` and `-fprofile-*` options: `ForbiddenFlag { flag }`, `forbidden_flag` (unchanged; regression guard)
- any other argument that starts with `-` and is not on the allow-list (every `--<name>`, every carrier, `-wrapper`, `-B`, `-fplugin*`, `-include`, `-x`, `-dumpdir`, and so on): new `OptionNotAllowed { flag }`, new token `option_not_allowed`
- trailing `-o`: `DanglingOutput`, `dangling_output` (unchanged; regression guard)
- trailing `-MF`, `-MT` or `-MQ`: `WriteRedirect { flag }`, `write_redirect` (kept: an unboundable depfile)
- trailing `-I`: `OptionNotAllowed { flag: "-I" }`, `option_not_allowed`
- an `-o` or `-MF` operand that resolves (lexically, against the entry's directory) outside the run root, or a directory or derived output outside it: `OutsideRunRoot { path }`, `outside_run_root` (unchanged)
- no top-level `-c` after a complete walk: `NotCompileOnly`, `not_compile_only`
- an unreadable toolchain file (the trusted copy or `stage/toolchain.cmake`) or `build/CMakeCache.txt` (WR-14): new token `toolchain_unreadable`
- WR-12: a CMake pair without the read-only toolchain copy when the record stage requires it, a build-written `stage/toolchain.cmake` beside the read-only copy, a copy that differs from the pins, or a consistency finding: `toolchain_changed` (the existing token)

The 02-20 tests keep their names, because 02-SECURITY.md cites them, and change their expected variants.

WR-12 mechanism (revised after the plan check). The CMakeCache.txt line and the compile commands are build-writable, end-state data that a forger restores together with the toolchain file. Checks on the compile commands also cannot see added flags. So the proof is that the build cannot write the file:
1. `mt testbed toolchains`, run through `run_offline` with no upstream code, writes the pinned text to `<work>/toolchain/<id>/<cfg>/toolchain.cmake`.
2. run_build mounts that directory read-only at `/opt/mt/toolchain`. The path is in the container's read-only root file system, beside the existing read-only `/opt/mt/pins.toml` and `/opt/mt/testbed` mounts, and outside both writable mounts.
3. The build stage, which is mt code that runs before any upstream code, refuses to configure unless the file equals the recomputed text. It passes `-DCMAKE_TOOLCHAIN_FILE=/opt/mt/toolchain/toolchain.cmake`, so the first configure, its try-compiles and any regeneration read the pinned text.
4. The record stage, run with `--read-only-toolchain`, compares the trusted copy (the same host file) with the recomputed text. It refuses a CMake pair without the copy, or with a build-written `stage/toolchain.cmake`, and records `toolchain_file_read_only: true`.

Why the mount is not inside the run directory, with evidence:
- `prepare_run` empties the run directory in place (capture.rs:1416-1435), so it would try to delete the mount point;
- a mount point whose parent directory is writable can be moved away together with that parent, and a new file created at the configured path.

The cache line and the contiguous-flag check stay as consistency checks and are named so. The container workflow's `toolchain-ro-control` step proves live, with run_build's docker flags, that writes to such a mount fail.

What remains unproven, stated in the module doc: upstream CMake code can load other CMake files or add flags of its own, for example by rewriting build-directory files that a regeneration reads. Those flags appear in the compile commands, which the allow-list gates and replay re-runs. Local in-process runs and the tests have no container. They fall back to the 02-20 end-state comparison, and the report says so (`toolchain_file_read_only: false`).

Cost to the evidence: the configure step's argv and the configure-time files CMakeCache.txt, CMakeFiles/Makefile.cmake and CMakeFiles/<ver>/CMakeSystem.cmake now name `/opt/mt/toolchain/toolchain.cmake`. None of them is in the testbed notices. CMakeFiles/Makefile2 does not name the toolchain path (measured), so the notices' Makefile2 hashes do not change.

WR-13 measurement. A new step in the container workflow's image-a job lists the spec files of the pinned toolchain. That job builds the image from the same sha256-pinned Arm tarball (`container/pins.toml` `[source.arm_gnu]`) that the published digest carries. testbed.yml is not touched, so the testbed notices stay comparable line for line with 02-20's.

   - Any `gh api` failure: stop and report, asking the founder to paste the job conclusions and annotation text.

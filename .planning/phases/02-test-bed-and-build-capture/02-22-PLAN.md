WR-12 mechanism (from the plan check of the joint plan). The CMakeCache.txt line and the compile commands are build-writable, end-state data that a forger restores together with the toolchain file. Checks on the compile commands also cannot see added flags. So the proof is that the build cannot write the file:
1. `mt testbed toolchains`, run through `run_offline` with no upstream code, writes the pinned text to `<work>/toolchain/<id>/<cfg>/toolchain.cmake`.
2. run_build mounts that directory read-only at `/opt/mt/toolchain`. The path is in the container's read-only root file system, beside the existing read-only `/opt/mt/pins.toml` and `/opt/mt/testbed` mounts, and outside both writable mounts.
3. The build stage, which is mt code that runs before any upstream code, refuses to configure unless the file equals the recomputed text. It passes `-DCMAKE_TOOLCHAIN_FILE=/opt/mt/toolchain/toolchain.cmake`, so the first configure, its try-compiles and any regeneration read the pinned text.
4. The record stage, run with `--read-only-toolchain`, compares the trusted copy (the same host file) with the recomputed text. It refuses a CMake pair without the copy, or with a build-written `stage/toolchain.cmake`, and records `toolchain_file_read_only: true`.

Why the mount is not inside the run directory, with evidence:
- `prepare_run` empties the run directory in place (capture.rs:1416-1435 at 295c4a5), so it would try to delete the mount point;
- a mount point whose parent directory is writable can be moved away together with that parent, and a new file created at the configured path.

The cache line and the contiguous-flag check stay as consistency checks and are named so. The container workflow's `toolchain-ro-control` step proves live, with run_build's docker flags, that writes to such a mount fail.

What remains unproven, stated in the module doc: upstream CMake code can load other CMake files or add flags of its own, for example by rewriting build-directory files that a regeneration reads. Those flags appear in the compile commands, which plan 02-21's allow-list gates and replay re-runs. Local in-process runs and the tests have no container. They fall back to the 02-20 end-state comparison, and the report says so (`toolchain_file_read_only: false`).

Cost to the evidence: the configure step's argv and the configure-time files CMakeCache.txt, CMakeFiles/Makefile.cmake and CMakeFiles/<ver>/CMakeSystem.cmake now name `/opt/mt/toolchain/toolchain.cmake`. None of them is in the testbed notices. CMakeFiles/Makefile2 does not name the toolchain path (measured), so the notices' Makefile2 hashes do not change.

WR-14 test. The host runs tests as uid 0, so a mode-000 file is still readable. WR-14 is therefore proven by a pure test of the mapping (`toolchain_file_finding`), together with the structural fact that `check_toolchain_file` has no error path.

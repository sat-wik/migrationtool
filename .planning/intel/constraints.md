## UB labeling and policy protocol
- source: SPEC (Technical approach problem 1; module 5)
- type: protocol
- content:
DATA_Zc84tRaN_START
Replay every fuzz and test input against a C build with AddressSanitizer, UndefinedBehaviorSanitizer and MemorySanitizer. Tagged inputs are checked against the UB policy instead of the C's output. Build the C at -O0 and at the customer's real flags; if the two disagree on an input, that input almost certainly hits undefined behavior. Run KLEE or an abstract interpreter such as Frama-C over parser functions to list problem sites the fuzzer never reached. Pin implementation-defined behavior to the target (plain char signedness, integer sizes, struct layout); every decision goes in the UB log for sign-off. UB decision menu: return an error, panic, or preserve.
DATA_Zc84tRaN_END

## Analysis-toolchain LLVM version lock (R1)
- source: VER (R1, KLEE and c2rust and Hayroll verdicts)
- type: nfr
- content:
DATA_Rf2jY8eM_START
KLEE 3.2 (23 Dec 2025): recommended LLVM 16, partial support for LLVM 17-19, LLVM < 13 removed; no Rust support mentioned. Hayroll: requires a single matching LLVM/Clang version, explicitly not LLVM 20. c2rust: LLVM/Clang 15 or later; needs exact compile commands via compile_commands.json; cross-architecture transpilation with a different sysroot. Action: pin one LLVM (16-19) for all C-side analysis; use a pinned older rustc whose LLVM is 19 or lower for bitcode emission (confirm with rustc -vV) or a different Rust-side symbolic engine; spike Rust-to-KLEE before promising per-function symbolic equivalence. ADR-0001 requires these tools to run as pinned subprocesses in a reproducible container.

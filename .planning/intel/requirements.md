## REQ-translate
- source: SPEC (module 3; customer requirement 3)
- description: c2rust and Hayroll front end, then agentic function-by-function translation in dependency order with a deterministic check after every step (compiles, no stubs, passes harness). Lift C idioms to safe Rust; target `no_std`, allocation-free from day one. Output: safe Rust with `unsafe` only at the C boundary, each unsafe block justified in writing; builds for customer targets (e.g. `thumbv7em-none-eabihf`); formatted, Clippy-clean, documented, pinned Rust version, minimal vetted dependencies.
- acceptance: Compiles for the target, contains no stubs or TODOs, `unsafe` only at the C boundary.
- scope: MVP

## REQ-validate
- source: SPEC (module 4; Technical approach problem 2)
- description: Layered equivalence engine: module-level differential fuzzing against the original C, per-function differential symbolic execution (KLEE), bounded model checking (Kani) for critical functions. Measure coverage on the C side. Divergence sends the module back to translation.
- acceptance: Zero divergences on defined-behavior inputs; branch coverage of the C at least 90% (proposed); every critical function has a bounded proof.
- scope: MVP (differential fuzzing + KLEE); v1 (Kani bounded proofs). Constrained by REQ-llvm-version-pin, REQ-spike-kani-c2rust-reference, REQ-target-matched-harness, REQ-sanitizer-variants.

## REQ-equivalence-contract
- source: SPEC (First 90 days step 2; Technical approach problem 1)
- description: Contract v0 is refinement, not equality: the Rust matches the C on every input where the C has defined behavior; on UB inputs the Rust takes a safe action from an approved menu (default: return an error, customer-adjustable) and never crashes or corrupts memory. ## Part C: Technical-risk requirements (VER, "Technical risks the spec does not mention")

VERIFICATION precedence 1 (above the spec) applies for facts; it does not override decisions. Each item below is a requirement or spike for the roadmap per VER.

## REQ-llvm-version-pin
- source: VER (R1)
- description: LLVM version lock across the analysis toolchain. KLEE supports LLVM 16 fully and 17-19 partially; Hayroll needs one matching LLVM/Clang and rejects LLVM 20; c2rust needs LLVM 15 or later. Current stable `rustc` ships a newer LLVM than KLEE supports, so "KLEE on both sides" needs either a pinned older `rustc` whose LLVM is 19 or lower for bitcode emission (confirm with `rustc -vV`) or a different Rust-side symbolic engine.
- acceptance: Pin one LLVM (16-19) for all C-side analysis; spike the Rust-to-KLEE path in the harness phase before promising per-function symbolic equivalence. (Pass criteria for the spike: absent.)
- scope: harness phase (MVP); affects REQ-validate

## REQ-spike-kani-c2rust-reference
- source: VER (R2)
- description: Using c2rust output as the reference for Kani equivalence is plausible but unproven (VERT used an rWasm reference). c2rust output calls libc through `extern "C"`, which Kani cannot execute without stubs or models; Kani misses aliasing violations and unaligned dereferences and does not reason about concurrency.
- acceptance: Treat as a spike with a go/no-go; write libc stubs; keep fuzzing plus KLEE as the primary evidence until the spike passes. (Go/no-go criteria: absent.)
- scope: MVP spike; Kani proofs in v1

## REQ-hayroll-licence-adapter
- source: VER (R3)
- description: Hayroll licence is unconfirmed in the repository view checked.
- acceptance: Confirm the licence (or get permission) before depending on it; isolate it behind an adapter so it can be swapped.
- scope: before translator phase (MVP)

## REQ-ferrocene-core-profile
- source: VER (R4); SPEC ([verified-fix] in functional safety paragraph)
- description: Ferrocene certifies only a subset of `core` (IEC 61508 SIL 2 / ISO 26262 ASIL B; 5,169 functions as of 26.02.0). Safety customers may require emitted Rust to call only certified `core` functions; output minimum Rust version must match the `rustc` inside the customer's Ferrocene release.
- acceptance: Add an output profile restricting emitted code to the certified `core` subset and to a pinned MSRV.
- scope: v1 (Ferrocene builds); v2 (qualification kit)

## REQ-target-matched-harness
- source: VER (R5)
- description: Host-versus-target ABI mismatch. Cortex-M is ILP32 with unsigned plain `char`; an x86-64 host is LP64 with signed `char`. A differential run on a default 64-bit host can disagree with the target, or agree with the other side and with neither.
- acceptance: Run the differential harness on an ILP32 configuration matching the target (e.g. `-m32`/i686, or Arm Linux under QEMU user mode) with `-funsigned-char` and the customer's flags; replay the final corpus on the real target or Renode.
- scope: harness phase (MVP)

## REQ-sanitizer-variants
- source: VER (R6)
- description: MemorySanitizer needs Clang, every linked object instrumented, and cannot share a build with AddressSanitizer.
- acceptance: Build separate ASan+UBSan and MSan variants of the C and replay the corpus against each.
- scope: harness phase (MVP)
